《深度学习500问》的重排版本，**公式在构建期就渲染成了 HTML**，因此整站不加载任何外部资源、不依赖运行时 JavaScript。断网能读，双击 `index.html` 就能看。

内容来自 [scutan90/DeepLearning-500-questions](https://github.com/scutan90/DeepLearning-500-questions)。正文文字未做任何改动，只修正了公式的写法问题（详见下文）。

## 为什么原版看起来像乱码

不是编码问题——原仓库所有 Markdown 文件都是干净的 UTF-8。真正的原因有两个：

**一是公式没被渲染。** 原站点靠 `unpkg`、`jsdelivr`、`cdnjs` 这三个 CDN 在浏览器里现场加载 MathJax/KaTeX。这些 CDN 在国内经常连不上，脚本一旦加载失败，全书 1900 多条公式就会退化成裸露的 LaTeX 源码：

```
$$\Vert\vec{x}\Vert_1=\sum_{i=1}^N\vert{x_i}\vert$$
```

满屏都是这个，看着就是乱码。本仓库把这一步挪到了构建期，产物里已经是渲染好的 HTML。

**二是原稿里有些公式写法本身有问题**，即使 CDN 正常也渲染不出来。构建脚本会自动修正这几类：

| 问题 | 例子 | 处理 | 次数 |
| --- | --- | --- | --- |
| 起始 `$` 前面不是空白，GitHub 因此不把它当作公式定界符 | `参数$\beta$来控制` | 前面补一个空格 | 868 |
| 公式内混入**零宽空格 U+200B**，同样破坏定界符判定 | `$\mu<U+200B>$` | 清除 | 195 |
| `$$` 定界符没有独占一行，整段被并成一个段落后按行内规则错误配对，把成片中文吞进数学模式 | `文字\n$$\n公式\n$$\n紧接着的文字` | 拆成独占行并补空行 | 309 |
| 两个行内公式紧挨着，前一个的结束符和后一个的起始符凑成假的 `$$` | `当$x=0$$f'(x)=0.25$` | 中间补一个空格 | 6 |
| 公式被反引号包住，渲染成等宽代码而不是公式 | `` `$U,W,b$` `` | 解开反引号 | 4 |
| `eqnarray` 环境 KaTeX 不支持 | `\begin{eqnarray}` | 转成等价的 `aligned` | 5 |
| 正文被误写进 `$$` 块内部（块外另有一份正确的重复） | 见 ch07 FID 一节 | 从块尾剥出来当普通段落 | 2 |
| 行内公式跨多行被截断（分段函数常见），`$` 的行内规则不跨行 | `$ f(x)=\\left\\{`…4 行…`\\right. $` | 合并成一行（须通过 KaTeX 校验） | 4 |
| 公式里的 `_` / `*` 与同行另一条公式配对成了斜体；表格单元格内 `\\` 被吃掉一个 | `$S^{-1}_{w} S_b$`、`$7*7*3$` | 改用 GitHub 的 ``$`...`$`` 写法 | 50 |
| 下标缺花括号，KaTeX 比多数 LaTeX 实现严格 | `_\boldsymbol w` | 补成 `_{\boldsymbol w}` | 1 |

占比最大的是**起始定界符前缺空白**那一类。这条规则不是照搬 CommonMark，而是抓取本仓库已发布页面、统计 GitHub 真实渲染结果反推出来的：

| 起始 `$` 前面的字符 | GitHub 渲染成功 | 失败 |
| --- | --- | --- |
| 空白 | 79 | — |
| 段落起始 | 2 | — |
| 汉字 | **0** | 137 |
| 标点 | **0** | 25 |

也就是说 GitHub 比 CommonMark 的 flanking 规则更严——起始 `$` 前面**必须**是空白或行首，是标点也不行。收尾的 `$` 则很宽松，后面接汉字、标点、空白都能正常渲染。这解释了为什么同一段里 `其中, $\mu$` 出得来、而 `参数$\beta$` 出不来。

**零宽空格**那一类完全不可见，在任何编辑器里都查不出来。剩下的 50 条则是 markdown 语法本身把公式改写了（`_`、`*` 跨公式配对成斜体，或表格单元格吃掉 `\\`），补空格无济于事，只能改用 GitHub 官方的 ``$`...`$`` 写法——实测其余候选写法（加花括号、四反斜杠、`\cr`）均无效。

判断哪条公式"脆弱"不靠人工枚举：构建时把公式所在行按普通 markdown 渲染一遍，若公式原文没能原样保留，就说明 markdown 动了它。全书 1644 条行内公式命中 50 条（3%），只对这 50 条改写；``$`...`$`` 是 GitHub 专有语法，其他编辑器不认，因此不全书铺开。

## 重新构建

Markdown 源文件在 `ch*/`，HTML 是生成物。改完源文件后重新生成：

```bash
cd tools
npm install
node build.js
```

`tools/build.js` 会重新渲染全部 20 个页面、刷新首页，把 KaTeX 的样式和字体拷进 `assets/`，并把修正后的 Markdown 写回源文件。

构建结束会打印每章的公式数、插图数和失败数——**失败数应当是 0**，不是 0 就说明源文件里有新的公式问题。脚本是幂等的：源文件已经规范的情况下再次运行，"回写 Markdown 源文件" 应当是 0 个。

跨行公式的合并有一道 KaTeX 校验作为闸门：只有合并后每条公式都能解析才会真的合并。所以文档里 `echo $NDK_ROOT` 这类 shell 变量不会被误当成公式黏合。

脚本读入时会先把上一次写下的 ``$`...`$`` 还原成普通写法再走流水线，渲染 HTML 前同样还原，所以 KaTeX 侧不受这个 GitHub 专有语法影响。
